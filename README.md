# MyHealth Uganda

**A Patient-Centered Digital Records Platform for Continuity of Care**

MyHealth Uganda is a mobile-first, offline-capable digital health records platform that gives patients ownership and control over their medical records. It enables seamless, secure data sharing across Uganda's fragmented health system through QR-code based sharing and integration with existing EMR systems such as OpenMRS and DHIS2.

The platform is developed under the TRANSPIRE initiative at the Mildmay Research Centre Uganda and aligns with Uganda's Digital Health Strategy 2020 to 2024 and the Data Protection and Privacy Act 2019.

## Problem and Solution

Uganda's health system suffers from fragmented medical records. Patient information is stored in paper-based files scattered across health facilities with little or no interoperability between health centres, private clinics, and referral hospitals. Patients must repeat tests and recount their medical histories at every visit. Continuity of care is lost for chronic illnesses including HIV, TB, diabetes, and hypertension. Resources are wasted on redundant testing because providers cannot access prior results.

MyHealth Uganda solves this by creating a patient-owned digital health wallet. Patients securely store their complete medical history in a mobile application and share it with any provider through a time-limited QR code. The platform integrates with existing systems through HL7 FHIR standards, works offline in low-connectivity settings, and logs every access for full compliance with Uganda's data protection laws.

## Architecture Overview

The system follows a layered architecture with clear separation of concerns.

The **Django Backend** handles authentication, business logic, REST and FHIR-compatible endpoints, consent management, and audit logging. **PostgreSQL** serves as the primary data store with application-level encryption for personally identifiable information. An **S3-compatible object store** handles patient document uploads such as lab report PDFs and scanned prescriptions. **Celery with Redis** processes background tasks including file processing, sync jobs, and notification delivery. The **mobile client** is a Progressive Web App with offline storage via IndexedDB, with an optional React Native wrapper for native biometric access. **Integration adapters** reconcile FHIR and HL7 messages with facility EMR systems including OpenMRS and DHIS2.

For the MVP deployment, the system runs on a small number of managed virtual machines with a separate database host, application host, and object store. Kubernetes is not required at this stage.

## Getting Started

### Prerequisites

You will need Python 3.11 or later, pip, and optionally Docker and Docker Compose for containerised deployment.

### Local Development Setup

Clone the repository and navigate into the project directory.

```bash
git clone https://github.com/your-org/myhealth-uganda.git
cd myhealth-uganda
```

Create a virtual environment and install dependencies.

```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

Copy the environment template and generate an encryption key.

```bash
cp .env.example .env
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Paste the generated key into the `FIELD_ENCRYPTION_KEY` variable in your `.env` file. Also generate a Django secret key and paste it into `DJANGO_SECRET_KEY`.

Run migrations and seed the demo data.

```bash
python manage.py migrate
python manage.py seed_demo
```

Start the development server.

```bash
python manage.py runserver
```

The API is now available at `http://localhost:8000/api/v1/` and interactive documentation is at `http://localhost:8000/api/docs/`.

### Docker Setup

For a fully containerised environment with PostgreSQL and Redis, simply run the following.

```bash
cp .env.example .env
docker compose up --build
```

Once the containers are running, seed the demo data inside the web container.

```bash
docker compose exec web python manage.py seed_demo
```

### Running Tests

The included smoke test validates all 21 core API endpoints.

```bash
python test_api.py
```

For the full Django test suite, run the following.

```bash
python manage.py test
```


## Web Application Frontend

A React-based web application built with Vite is included in the `frontend/` directory. It consumes this Django API and provides role-specific dashboards for patients, providers, and administrators.

To run the full stack locally, start Django first, then start the frontend in a separate terminal.

```bash
# Terminal 1: Django backend
python manage.py runserver

# Terminal 2: Vite frontend
cd frontend
npm install
npm run dev
```

Open your browser to `http://localhost:3000` and sign in with the demo credentials listed above. The frontend automatically handles JWT authentication with token refresh, and CORS is pre-configured between port 3000 and port 8000.

See `frontend/README.md` for full documentation on the web application including the page reference, authentication architecture, and styling philosophy.

## QR Sharing Flow

The QR sharing system is the core patient empowerment feature that enables rapid provider access without requiring the provider to create a full account.

The patient opens the MyHealth app and requests a QR code, specifying which data categories to share and for how long. The backend creates a cryptographically signed, short-lived token stored in the ShareToken table and returns a QR code image encoded in base64. The provider scans the QR code using their device or the provider web app. The system calls the verification endpoint, validates that the token exists, has not expired, and has not already been used. Upon successful verification, the system automatically creates a Consent record granting the provider time-limited access to the patient's selected records. Every access is logged in the immutable audit trail.

Tokens are single-use by default and can be revoked by the patient at any time. The maximum token lifetime is 24 hours, with a default of 10 minutes.

---

## FHIR Interoperability

The platform provides a pragmatic FHIR compatibility layer rather than attempting to be a fully certified FHIR server at the MVP stage. The system maps core local models to standard FHIR resources for export and import.

Outbound exports convert Django model instances into FHIR JSON for Patient, Encounter, Observation, and DiagnosticReport resources. The `$everything` endpoint wraps all of a patient's data into a FHIR Bundle for bulk export. Inbound integration accepts FHIR Bundles from facility EMR systems and maps the entries to local models.

For facility EMR integration with OpenMRS, the system accepts data through a signed API request using HMAC with pre-shared integration keys. For DHIS2, the analytics module aggregates counts and pushes metrics through the DHIS2 API.

## Security and Privacy

The platform is designed for compliance with Uganda's Data Protection and Privacy Act 2019 and follows privacy-by-design principles throughout.

**Transport security** is enforced through TLS 1.2 or later on all endpoints with HSTS enabled in production. **Authentication** uses JWT with short-lived access tokens of 30 minutes and refresh tokens of 7 days with automatic rotation. **Authorization** implements role-based access control across four roles: Patient, Provider, Facility Admin, and System Admin. Object-level permissions ensure patients can only access their own records and providers can only access records for which they have active consent.

**Personally identifiable information** including phone numbers and addresses is encrypted at rest using Fernet symmetric encryption with keys managed through environment variables for the MVP and cloud KMS in production. National ID Numbers are stored only as salted SHA-256 hashes and are never persisted in plaintext.

**Audit logging** captures every read and write operation on patient data in an immutable, append-only log. Entries cannot be modified or deleted at the application level. The audit trail records the actor, action, target resource, IP address, and timestamp for every request.

**Rate limiting** protects API endpoints from abuse with configurable thresholds of 30 requests per minute for anonymous users and 120 requests per minute for authenticated users.

## Deployment

### MVP Deployment

For the initial pilot with 3 to 5 health facilities, the recommended deployment uses managed cloud services with a single application server running Gunicorn behind a reverse proxy, a managed PostgreSQL instance for the database, an S3-compatible object store for patient documents, and a Redis instance for Celery task queuing.

Docker Compose handles orchestration for the MVP. Copy the environment template, update the database credentials and encryption keys, and run the following.

```bash
docker compose up -d
docker compose exec web python manage.py migrate
docker compose exec web python manage.py seed_demo
```

### Production Considerations

For national scale-up, the architecture supports horizontal scaling with read replicas for PostgreSQL, autoscaling application servers behind a load balancer, and a dedicated Redis cluster. Monitoring uses Prometheus with Grafana for metrics, Sentry for error tracking, and structured JSON logging shipped to a centralised system.

## Roadmap

The development roadmap follows the phased approach from the business plan with a lean MVP budget of $60,000 over 12 months.

**Phase 1: Product Development and Compliance (Months 1 to 4, $28,000)**
This phase covers the core backend API, patient health wallet, QR sharing engine, FHIR integration with a single EMR system, the Android PWA, legal compliance with the Data Protection Act, and the data governance framework. The current codebase represents substantial completion of the backend portion of this phase.

**Phase 2: Pilot Deployment and Validation (Months 5 to 8, $21,000)**
This phase covers deployment to 2 pilot clinics, on-site EMR integration, health worker training, patient enrollment campaigns, community engagement through Village Health Teams, and monitoring and evaluation to measure impact on redundant testing and care continuity.

**Phase 3: Go-to-Market and Fundraising Readiness (Months 9 to 12, $11,000)**
This phase covers professional branding and logo design, a demo video for grant applications, the investor pitch deck built on pilot data, grant applications to 3 to 5 relevant funding bodies, stakeholder meetings with the Ministry of Health and NITA-U, and registration of the Social Enterprise SPV for commercial operations.

The pilot success metrics will demonstrate readiness for the $1,000,000 scale-up investment covering national rollout to regional referral hospitals, private clinics, and integration with the national health insurance framework.
